# Modelling for the Kiln engine

Geometry here is **generated by Python, not sculpted**. Every model in
PetaByte-Madness that was imported as art (`island_n64.obj`,
`dank_lab.obj`) had to be reverse-engineered before the runtime could use
it, and every one that was generated (`pm_env.py`, `pm_world.py`) worked
first time. The pipeline is built for the generated case.

## The one rule that prevents most bugs

**Never type a dimension into C that geometry already defines.**

Every camera and collision defect in this project has had that shape: an
island placed at a tenth of its size, a lab shot opening 69 units behind a
wall, a flyover key at 1.4 island radii that flew through the ridges, palm
trees scaled 40× until each was taller than the island.

The fix is mechanical. The generator measures itself and emits a header:

```bash
python3 tools/blender/pm_world.py --emit-header PetaByte-Madness/src/pm_world_gen.h
```

C then derives from `PM_ISLAND_RADIUS`, `PM_LAB_Z0`, `PM_GATE_TABLE`… and a
camera orbit becomes `radius * 2.4` rather than `15000`. Tests derive their
sample points the same way — a test that restates a dimension drifts from
it exactly like the code did.

Two emitters exist; both are gated by `nix/checks/pm-gen-headers.nix`, which
diffs the committed header against a fresh run:

```bash
python3 tools/blender/pm_world.py --emit-header \
    PetaByte-Madness/src/pm_world_gen.h                  # island, gates, tower
python3 PetaByte-Madness/tools/dank_lab_gen.py --emit-header \
    PetaByte-Madness/src/pm_lab_gen.h                    # lab, MRI, desk, lights
```

**A generator can only publish what it names.** `dank_lab_gen.py`'s scanner
centre and stool position were function locals, which is *why* `pm_lab.h` had
`#define PM_LAB_DESK_X (113.92f) // STOOL_X (178) * 0.64` — with the arithmetic
in a comment. Lifting them to module constants was the whole fix. If a dimension
matters to the runtime, give it a name at module scope.

**A generator that is not on the build path can still drift.** `dank_lab_gen.py`
emitted `assets/obj/dank_lab.obj` once and the ROM ships that OBJ; the header
comes from the generator. So the two can part company while both look fine —
which is why `pm-gen-headers` also compares the generator's measured bbox
against the committed OBJ's. Triangle counts are reported, not gated (they
already differ, harmlessly).

## Units

- Author **in metres**. `gltf_to_t3d` is invoked with `--base-scale=64`
  (`nix/blender.nix`), and the world runs at **64 units per metre**
  (`pm_lab.h`). So 1 Blender unit = 1 metre = 64 world units, and nothing
  downstream needs a scale factor.
- Blender is **+Z up**; the exporter converts to the engine's **+Y up**.
- Vertex positions are **int16** after export. At scale 1 that is ±32,767
  world units — fine for a 200 m island, and the reason to draw at scale 1
  rather than authoring small and scaling up: at a draw scale of 100, one
  vertex unit is 100 world units and any small displacement (a swell, a
  step) rounds to zero.

## Vertex colours

- `make_mesh(colors=…)` wants **linear float RGBA**. Use `kilnlib.srgb(r,g,b)`
  which takes 0–255 sRGB and inverts the gamma `gltf_to_t3d` applies. Passing
  raw ints fails with *"sequences of dimension 0 should contain 4 items,
  not 3"*; passing sRGB floats double-gammas.
- Keep builders returning readable 0–255 tuples and convert at the Blender
  boundary — that keeps the builders importable by tests that have no bpy.
- **Separate colours by VALUE, not hue.** The veil collapses hue
  (`docs/VEIL_DESIGN.md` §4), so a palette distinguished only by hue stops
  reading. Few, flat, value-separated.

## Materials and textures

- `gltf_to_t3d` **aborts** on a glTF material with no fast64 data. Either
  `ignoreMaterials = true` (untextured test assets) or let
  `tools/f3d_inject.py` write the block: `materials = [ "*=shade" ]`, or
  `"water=tex0_shade,tex=textures/foam.i8.png,size=32"`.
- Texture filenames are **`<name>.<fmt>.png`** and two tools parse that
  middle section. Keep to it.
- `tools/gen_textures.py`'s `write_png` **always emits RGBA8** — the `.i8.`
  in the name only tells `mksprite` what to quantise *to*. Emitting one byte
  per pixel because the target is I8 produces a PNG whose IDAT is a quarter
  the promised length and fails three tools later as *"invalid decompressed
  idat size"*.
- **TMEM is 4 KB and the Expansion Pak does not change that.** At 32×32:
  I8 = 1 KB, IA8 = 1 KB, RGBA16 = 2 KB.
- A scrolling texture must tile. `value_noise` wraps at `period`; **scaling a
  sample coordinate breaks the wrap**. Measure the seam against the *typical
  adjacent* row/column difference of the raw field, not the finished bytes —
  a hard threshold turns a 0.01 field difference into a 30-value jump and
  reads as a seam where the field is continuous.

## CI4 and the veil's palette contract

A CI4 texture is 4 bpp — 2 KB at 64×64 against a 4 KB TMEM, where RGBA16 would
be 8 KB and could not load at all. It is also the format the scarlet veil is
built on: swap the 16-entry TLUT and the whole material changes colour for 32
bytes of DMA and zero extra shaded pixels.

Use `assetLib.mkVeilTexture` (not `mkSprite`) for anything the veil affects. It
emits the `.sprite` **and** a 64-byte `.pal` (16 cold + 16 veiled, RGBA5551
big-endian) from ONE derivation, because two derivations would be two
independent quantisations of the same image and the texel indices would address
the wrong colours — a model that renders, in the wrong palette, with nothing
failing.

- **The source must already be indexed** (PIL mode `P`, ≤16 colours).
  `tools/veil_palette.py` reads the PNG's own palette; a truecolour source would
  be quantised twice, differently. `mc_face.png` / `mc_plate.png` /
  `mc_gore.png` are real examples.
- **`veilClass` is the consequential parameter** (`world` / `demon` / `phantom` /
  `eyes`, VEIL_DESIGN.md §4). Under the veil hue carries nothing and only value
  does, so value is rationed: `world` collapses into a mid band and may not own
  black or white; `demon` owns both ends, and that contrast is what drags the
  eye. `phantom` is alpha 0 on **every** cold entry — the creature is not drawn
  at all with the veil down — so getting it wrong shows the player a monster the
  design says they cannot see yet. `eyes` keeps the brightest four.
- This is why the palette rule higher up ("separate by VALUE, not hue") is
  load-bearing rather than stylistic: the veil literally discards hue.
- `python3 tools/veil_palette.py --selftest` asserts all of the above.

## Geometry that the runtime can use

- **Walkable surfaces must be flat**, at as few distinct heights as possible.
  `kiln_clip` collides axis-aligned boxes; a sculpted slope has nothing to
  bind to and every brush becomes a guess.
- **Name sub-objects** for anything gameplay refers to (`gates`, `terrain`,
  `tower`). `t3d_model_get_object` finds them; `kiln_room`/`kiln_actor` hang
  off them.
- **Never leave two surfaces coplanar.** An island rim ending at exactly
  sea level, with the sea plane at the same height, z-fights along the whole
  coast and reads as the island glitching. Carry the terrain *below* the
  water and let the water start *inside* the island: the waterline should be
  an intersection of two solids, not a shared surface.
- Budgets that held at 60 fps: island terrain ~830 tris, six gates 288,
  skydome 408, sea 504, lab 264. **Fill rate, not triangle count, is the
  limit** — a full-screen sea plus sky is the expensive part.

## Determinism

No `random`, no wall-clock, no dict-iteration order — `nix/checks/assets.nix`
builds twice and compares. For irregularity use a few chosen harmonics
(`coast_wobble`) or an integer hash (`_hash2`).

## Test without Blender first

Builders must import no `bpy` and return plain `(verts, faces, colors[, uvs])`.
`tools/blender/test_env.py` and `test_world.py` then check the properties the
runtime depends on in milliseconds:

```bash
python3 tools/blender/test_world.py
```

Check *structure*, not looks: flat things flat, indices in range, budgets,
gates on their bearings, the rim crossing the waterline exactly once. This
caught a wrong plane-intersection formula and an inverted winding in
`quake_map.py` before Blender ran once, and caught three real faults in
`pm_world.py`.

## Is the model's light already IN it?

Before choosing a runtime rig, find out whether the asset's vertex colours are
albedo or already-shaded. This is the single easiest way to make a room look
unlit, and it looks like a lighting bug rather than a double-application.

`dank_lab_gen.py` bakes a twelve-fixture rig into its vertex colours before
writing the OBJ, and marks textured surfaces `LIT_WHITE` precisely so "the shade
channel should be pure lighting". The runtime was then lighting it a *second*
time with one directional light and the engine's bootstrap `ambient = 45` — a
generic avoid-pure-black floor from `kiln_engine.c`, never chosen for any room —
and the product of two darkenings is what "the lab is unreadable" was.

- **Pre-baked colours want a near-unity runtime rig**: enough directional
  variation that geometry reads as shape rather than flat paint, and enough
  ambient that a face turned from the key does not crush. Not a moody rig.
- **Do not install a generator's rig verbatim.** Its intensities and its
  `AMBIENT` are the parameters of a *bake* (the lab's is 15/21/23 of 255), not an
  exposure for a renderer.
- **What the authored rig IS good for is direction**, so the runtime's highlights
  land where the baked ones already are. `pm_env_interior_from_rig` takes the two
  fixtures with most influence at the shot's look target and uses only their
  directions, pulling colour most of the way to white.
- A directional light's `dir` is the direction light **travels** — from the
  fixture toward the subject. Backwards lights the far side of everything, which
  reads as inside-out geometry and is invisible in a still of a symmetric room.

## Lighting and atmosphere (KilnScene)

- Tiny3D supports **7 directional + 7 point lights** and
  `t3d_light_set_exposure`. `KilnScene` carries `KILN_SCENE_MAX_LIGHTS`;
  `light_color`/`light_dir` are light 0.
- One light alone leaves every shadowed face at flat ambient, which on
  curved terrain reads as **a hole in the mesh, not as darkness**. Use a key
  plus a dim fill.
- Fog is nearly free and is the cheapest thing that makes distance read.
  `kiln_scene_set_fog(scene, colour, near, far)`. **Fog ranges are
  camera-relative** — a range that sounds right for the size of the subject
  is usually wrong for the distance to it. Sizing fog from the island's
  radius instead of the camera's distance drew the whole island as a flat
  silhouette in the fog colour, which looked like a hole in the sea.
- Match the **horizon colour** across sky dome, sea rim and fog. That
  three-way match is what makes a finite water plane end invisibly.
- A skydome is drawn first, unlit, **depth off**, centred on the camera —
  then it can never clip, occlude, or be reached, and its radius is
  arbitrary.

## Cameras

- **A cut should cut.** `KILN_CAM_CUTSCENE` follows its pose exactly; it must
  not damp. Damping authored keyframes double-smooths them, lags the look
  target, and — worst — makes a cut between shots *travel*, flying the
  camera across the world and through whatever is in the way.
- Derive framing from measured extents. A useful starting point: orbit at
  ~2.2–2.6 × the subject's radius, eye above its highest point, look a third
  of the way up its mass.

## Verifying

`nix build` proves it links, not that it looks right. **The whole verification
ladder is its own skill — load `n64-verify`.** The short version:

```bash
nix build .#pm-jump-lab                     # boots straight into that screen
./dev shot pm-jump-lab out.png 6            # no controller needed
```

Each `pm-jump-<screen>` ROM also switches on the spatial overlay that screen is
worth inspecting with, so a single capture shows the geometry AND the collision
boxes, actor positions, camera path or anchor gizmos next to it. `kiln_debugdraw`
is the module; **use it rather than reasoning about coordinates** — it is what
found a camera 1.7 m under the floor and a room with no collision at all.

**Trust the pixel statistics, not your eyes** (CLAUDE.md), and treat a
non-black percentage that does not move across an animated shot as evidence that
nothing is reaching the ROM. For framing, take several frames and montage them;
a single frame cannot show a camera drifting into terrain:

```bash
for t in 4 8 12 16; do ./dev shot pm-jump-intake f$t.png $t; done
montage f*.png -tile 2x2 -geometry +4+4 contact.png
```

## Adding a model

1. Write the builder in `tools/blender/<name>.py`, bpy-free, returning
   `(verts, faces, colors)`; convert with `m.srgb` in `main()` only.
2. Write checks in `tools/blender/test_<name>.py`. The name matters: `test_*.py`
   is the glob `nix/checks/blender-tests.nix` gates and must run under a bare
   `python3`; `blender_test_*.py` is for the rare test that genuinely needs a
   live Blender and is deliberately excluded.
3. Add the derivation in `flake.nix`:
   `pmThing = blenderLib.mkBlenderModel { name = "thing"; script = "<name>.py"; };`
   with `materials`/`textures` if it is textured, `bvh = false` for anything
   always on screen. (Note `bvh = false` everywhere is why frustum culling is
   unavailable in this game — `t3d_model_bvh_query_frustum` has nothing to read.)
4. Add it to the ROM's `assets` list and to `PM_MODEL_LIST` in `pm_models.h` —
   ONE entry there generates the enum, the DFS path and the overlay label, so
   they cannot drift. **The asset's `name` IS its filename**: check it against
   the path the C actually opens, because a mismatch is silent all the way down
   (it cost PetaByte Madness its entire PLAY screen).
5. **`git add` it** — Nix flakes only see tracked files, and an untracked
   source fails as *"No such file or directory"* inside the sandbox.
6. Emit/refresh any generated header (`pm-gen-headers` will fail otherwise),
   then build and capture.
