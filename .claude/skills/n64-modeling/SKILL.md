# Modelling for the Kiln engine

Geometry here is **generated by Python, not sculpted**. A model imported as
art (an `.obj`/`.glb` drop) has to be reverse-engineered before the runtime
can use it reliably, while a model generated by a script that measures its
own output tends to work the first time. The pipeline is built for the
generated case; `tools/blender/goblin.py`, `interceptor.py`, `droid.py`,
`alien.py` and the primitive builders in `kilnlib.py` are this repo's own
worked examples.

## The one rule that prevents most bugs

**Never type a dimension into C that geometry already defines.**

The camera and collision defects this project has hit have all had that
shape: something placed at a tenth of its real size, a shot opening dozens of
units behind a wall it should have cleared, a flyover key that flew through
terrain it should have orbited, props scaled tens of times too large.

The fix is mechanical. A generator that owns a dimension should measure
itself and emit a header:

```bash
python3 tools/blender/<generator>.py --emit-header src/<generator>_gen.h
```

C then derives from the emitted constants — a camera orbit becomes
`radius * 2.4` rather than a literal `15000`. Tests derive their sample
points the same way — a test that restates a dimension drifts from it
exactly like the code did. Gate the generated header with a `nix/checks/*.nix`
that diffs the committed file against a fresh run, the same way
`nix/checks/kiln-font.nix` does for a generated font table.

**A generator can only publish what it names.** A dimension that starts life
as a function-local variable can't be emitted; lifting it to a module-scope
constant is the whole fix, and it is worth doing the moment a second piece of
code (a test, a C header, another generator) needs the same number. Comments
like `// STOOL_X * 0.64` with the arithmetic written out in prose are the
tell that a real named constant is overdue.

**A generator that is not on the build path can still drift from the content
it describes.** If a generator's own OBJ/glTF output is committed separately
from its emitted header (rather than always regenerated), the two can part
company while both look fine — worth a gate that also compares the
generator's measured bounds against the committed geometry file, not just
regenerating the header in isolation.

## Units

- Author **in metres**. `gltf_to_t3d` is commonly invoked with
  `--base-scale=64` (`nix/blender.nix`'s `mkBlenderModel`), so 1 Blender unit
  = 1 metre = 64 world units is a reasonable project-wide convention, and
  nothing downstream needs a scale factor once it's picked.
- Blender is **+Z up**; the exporter converts to the engine's **+Y up**.
- Vertex positions are **int16** after export. At scale 1 that is ±32,767
  world units — fine for content on the order of hundreds of metres, and the
  reason to draw at scale 1 rather than authoring small and scaling up: at a
  draw scale of 100, one vertex unit is 100 world units and any small
  displacement (a swell, a step) rounds to zero.

## Vertex colours

- `make_mesh(colors=…)` wants **linear float RGBA**. Use `kilnlib.srgb(r,g,b)`
  which takes 0–255 sRGB and inverts the gamma `gltf_to_t3d` applies. Passing
  raw ints fails with *"sequences of dimension 0 should contain 4 items,
  not 3"*; passing sRGB floats double-gammas.
- Keep builders returning readable 0–255 tuples and convert at the Blender
  boundary — that keeps the builders importable by tests that have no bpy.
- **Separate colours by VALUE, not hue, for anything a palette-swap mechanic
  might affect** (see "CI4 and a palette-swap contract" below) — a filter
  that collapses hue makes a palette distinguished only by hue stop reading
  entirely. Few, flat, value-separated colours degrade gracefully either way.

## Materials and textures

- `gltf_to_t3d` **aborts** on a glTF material with no fast64 data. Either
  `ignoreMaterials = true` (untextured test assets) or let
  `tools/f3d_inject.py` write the block: `materials = [ "*=shade" ]`, or
  `"water=tex0_shade,tex=textures/foam.i8.png,size=32"`.
- Texture filenames are **`<name>.<fmt>.png`** and two tools parse that
  middle section. Keep to it.
- `tools/gen_textures.py`'s `write_png` **always emits RGBA8** — the `.i8.`
  in the name only tells `mksprite` what to quantise *to*. Emitting one byte
  per pixel because the target is I8 produces a PNG whose IDAT is a quarter
  the promised length and fails three tools later as *"invalid decompressed
  idat size"*.
- **TMEM is 4 KB and the Expansion Pak does not change that.** At 32×32:
  I8 = 1 KB, IA8 = 1 KB, RGBA16 = 2 KB.
- A scrolling texture must tile. `value_noise` wraps at `period`; **scaling a
  sample coordinate breaks the wrap**. Measure the seam against the *typical
  adjacent* row/column difference of the raw field, not the finished bytes —
  a hard threshold turns a 0.01 field difference into a 30-value jump and
  reads as a seam where the field is continuous.

## CI4 and a palette-swap contract

A CI4 texture is 4 bpp — 2 KB at 64×64 against a 4 KB TMEM, where RGBA16 would
be 8 KB and could not load at all. It is also the format any palette-swap
mechanic (Forge's veil-capable atlas is the reference — see the `n64-forge`
skill) is built on: swap the 16-entry TLUT and the whole material changes
colour for 32 bytes of DMA and zero extra shaded pixels.

`assetLib.mkVeilTexture` (not `mkSprite`) is the tool for anything a
palette-swap effect affects. It emits the `.sprite` **and** a 64-byte `.pal`
(two 16-colour palettes, RGBA5551 big-endian) from ONE derivation, because
two derivations would be two independent quantisations of the same image and
the texel indices would address the wrong colours in one of them — a model
that renders, in the wrong palette, with nothing failing.

- **The source must already be indexed** (PIL mode `P`, ≤16 colours).
  `tools/veil_palette.py` reads the PNG's own palette; a truecolour source
  would be quantised twice, differently.
- **The class/category parameter is the consequential one** if you build a
  system like this: under a hue-discarding filter, only value carries, so
  value has to be rationed deliberately per category of content — some
  things should own the bright end for contrast, some should be invisible
  entirely under the filter (alpha 0 on every "filtered" palette entry), and
  getting a category wrong shows the player something the design says they
  shouldn't see yet, or hides something they should.
- This is why "separate by VALUE, not hue" above is load-bearing rather than
  stylistic for content meant to survive a palette swap.

## Geometry that the runtime can use

- **Walkable surfaces must be flat**, at as few distinct heights as possible.
  `kiln_clip` collides axis-aligned boxes; a sculpted slope has nothing to
  bind to and every brush becomes a guess.
- **Name sub-objects** for anything gameplay refers to (e.g. `gates`,
  `terrain`, `tower`). `t3d_model_get_object` finds them; `kiln_room`/
  `kiln_actor` hang off them.
- **Never leave two surfaces coplanar.** Terrain ending at exactly sea level,
  with a water plane at the same height, z-fights along the whole coastline
  and reads as the terrain glitching. Carry the terrain *below* the water and
  let the water start *inside* the land: the waterline should be an
  intersection of two solids, not a shared surface.
- **Fill rate, not triangle count, is the limit** on this hardware — a
  full-screen sea plus sky is typically the expensive part of a scene, not a
  few hundred extra triangles of terrain detail.

## Determinism

No `random`, no wall-clock, no dict-iteration order — `nix/checks/assets.nix`
builds twice and compares. For irregularity use a few chosen harmonics or an
integer hash.

## Test without Blender first

Builders must import no `bpy` and return plain `(verts, faces, colors[, uvs])`.
`tools/blender/test_*.py` (`test_goblins.py`, `test_objkit.py`, `test_prims.py`
in this repo) then check the properties the runtime depends on in
milliseconds — structure, not looks: flat things flat, indices in range,
budgets, a rim crossing a waterline exactly once. This discipline has caught
a wrong plane-intersection formula and an inverted winding in `quake_map.py`
before Blender ever ran, and it is the fastest feedback loop in the whole
geometry pipeline — see `nix/checks/blender-tests.nix`'s own header comment
for why it was ungated for most of its life and what that cost.

## Is the model's light already IN it?

Before choosing a runtime rig, find out whether an asset's vertex colours are
albedo or already-shaded. This is the single easiest way to make a room look
unlit, and it looks like a lighting bug rather than a double-application: a
generator that bakes a fixture rig into its vertex colours, paired with a
runtime that then lights the same geometry a *second* time with its own
directional light and a generic non-zero ambient, produces the product of
two darkenings — which is what "the room is unreadable" often actually is.

- **Pre-baked colours want a near-unity runtime rig**: enough directional
  variation that geometry reads as shape rather than flat paint, and enough
  ambient that a face turned from the key does not crush. Not a moody rig.
- **Do not install a generator's bake-time rig verbatim as a runtime rig.**
  Its intensities and ambient are the parameters of a *bake*, not an exposure
  setting for a live renderer.
- **What an authored bake rig IS good for is direction** — taking only the
  directions of its most influential fixtures (not their brightness) lets a
  runtime's own highlights land where the baked ones already are, pulling
  colour mostly toward white rather than re-tinting the scene.
- A directional light's `dir` is the direction light **travels** — from the
  fixture toward the subject. Backwards lights the far side of everything,
  which reads as inside-out geometry and is invisible in a still of a
  symmetric room.

## Lighting and atmosphere (KilnScene)

- Tiny3D supports **7 directional + 7 point lights** and
  `t3d_light_set_exposure`. `KilnScene` carries `KILN_SCENE_MAX_LIGHTS`;
  `light_color`/`light_dir` are light 0.
- One light alone leaves every shadowed face at flat ambient, which on
  curved terrain reads as **a hole in the mesh, not as darkness**. Use a key
  plus a dim fill.
- Fog is nearly free and is the cheapest thing that makes distance read.
  `kiln_scene_set_fog(scene, colour, near, far)`. **Fog ranges are
  camera-relative** — a range that sounds right for the size of the subject
  is usually wrong for the distance to it. Sizing fog from a subject's own
  radius instead of the camera's distance to it can draw the whole subject as
  a flat silhouette in the fog colour, which looks like a hole in the world.
- Match the **horizon colour** across sky dome, sea/ground rim and fog. That
  three-way match is what makes a finite ground/water plane end invisibly.
- A skydome is drawn first, unlit, **depth off**, centred on the camera —
  then it can never clip, occlude, or be reached, and its radius is
  arbitrary.

## Cameras

- **A cut should cut.** `KILN_CAM_CUTSCENE` follows its pose exactly; it must
  not damp. Damping authored keyframes double-smooths them, lags the look
  target, and — worst — makes a cut between shots *travel*, flying the
  camera across the world and through whatever is in the way.
- Derive framing from measured extents. A useful starting point: orbit at
  ~2.2–2.6 × the subject's radius, eye above its highest point, look a third
  of the way up its mass.

## Verifying

`nix build` proves it links, not that it looks right. **The whole
verification ladder is its own skill — load `n64-verify`.** The short
version: build a jump ROM that boots straight into the screen you care about
and needs no controller, then read `./dev shot`'s pixel statistics rather
than your eyes. `kiln_debugdraw` is the module for making the invisible
(collision boxes, actor positions, a camera path or anchor gizmos) show up in
that same capture — use it rather than reasoning about coordinates.

For framing, take several frames and montage them; a single frame cannot show
a camera drifting into terrain:

```bash
for t in 4 8 12 16; do ./dev shot my-jump-rom f$t.png $t; done
montage f*.png -tile 2x2 -geometry +4+4 contact.png
```

## Adding a model

1. Write the builder in `tools/blender/<name>.py`, bpy-free, returning
   `(verts, faces, colors)`; convert with `m.srgb` in `main()` only.
2. Write checks in `tools/blender/test_<name>.py`. The name matters: `test_*.py`
   is the glob `nix/checks/blender-tests.nix` gates and must run under a bare
   `python3`; `blender_test_*.py` is for the rare test that genuinely needs a
   live Blender and is deliberately excluded.
3. Add the derivation in `flake.nix`:
   `thingModel = blenderLib.mkBlenderModel { name = "thing"; script = "<name>.py"; };`
   with `materials`/`textures` if it is textured, `bvh = false` for anything
   always on screen (note: this engine has no frustum culling at all today —
   see CLAUDE.md's "What genuinely does not exist" — so `bvh` only matters
   once/if that changes).
4. Add it to the ROM's `assets` list. If the game has an X-macro-style asset
   table (name → enum/path/label, generated from one list), add it there
   too — the point of that pattern is that one entry generates everything
   else so they cannot drift. **The asset's `name` IS its filename**: check
   it against the path the C actually opens, because a mismatch is silent
   all the way down and has cost a real PLAY screen once already.
5. **`git add` it** — Nix flakes only see tracked files, and an untracked
   source fails as *"No such file or directory"* inside the sandbox.
6. Emit/refresh any generated header, and make sure its regeneration gate
   passes, then build and capture.
