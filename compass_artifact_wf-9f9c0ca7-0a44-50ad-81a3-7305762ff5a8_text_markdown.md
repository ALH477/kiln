# Faust DSP on Nintendo 64 / ModRetro M64: A Technical Feasibility Report

## TL;DR
- **A hybrid architecture is the only realistic path**: bake the bulk of your Faust physical-modeling voices offline to VADPCM/Opus sample banks via libdragon's audioconv64, and run a *small* amount of live Faust synthesis (a handful of voices) on the VR4300 in single precision, with the RSP reserved for the mixer. Pure real-time on-console Faust at your normal `-double -ftz 2` house style is not feasible — double `DIV.D` costs 58 cycles and there is no hardware FPU datapath.
- **The ModRetro M64 is the wrong development target but a fine deployment target.** It is a closed FPGA reimplementation (16 nm AMD Artix UltraScale+) that plays original carts and flashcarts (SummerCart64 confirmed working; EverDrive X7 enabled via an OTA firmware update and still being smoothed out) but exposes **no** developer USB/debug path to the cartridge and outputs fixed 48 kHz/16-bit PCM over HDMI. Develop on the Ares emulator + a real N64 (NUS-001) with a SummerCart64 over USB; treat the M64 as a "does my ROM run on FPGA" validation box.
- **Networking for SSHitunneller! works only via a host-PC proxy.** Use buu342's N64-NetLib pattern: terminate SSH on a PC, translate to a simple UDP/binary protocol, and tunnel over the flashcart USB link (~23.8 MiB/s peak on SummerCart64). Streamed control data driving client-side Faust synthesis is feasible; streaming audio is not needed and would waste the link.

## Key Findings
1. The M64 is an FPGA N64 clone, not a devkit. It has no cartridge-side USB, so your edit-build-test loop must use a SummerCart64 on original/clone hardware.
2. libdragon (not libultra) is the correct SDK: modern GCC 14, RSP microcode toolchain (RSPL), an RSP-accelerated 32-channel mixer, wav64/VADPCM/Opus, XM64, and USB debug via UNFLoader/`debugf()`.
3. The Faust C/C++ backend targets the VR4300 cleanly; the fixed-point backend is still experimental (Syfala/FAST project) and not production-ready. Single precision is mandatory; double is ruinously expensive.
4. Realistic live-synthesis budget on the VR4300 is small — on the order of a few waveguide voices or a dozen biquads — because every FP divide stalls the shared integer/FP pipeline.
5. Hand-porting Faust inner loops to RSP vector microcode is the high-effort/high-reward path: the RSP's 8-lane 16-bit SIMD is ideal for fixed-point biquads and delay lines but hostile to the numerics of high-Q feedback loops.

## Details

### 1. The ModRetro M64

**What it is.** Announced by Palmer Luckey's ModRetro in July 2025 at a teaser price of $199.99 ("Inflation isn't nostalgic," matching the 1997 N64 launch price), the M64 launched on July 28, 2026 at $229.99 standard ($199 early-bird), with the M64 Pro controller at $89.99. It is built around a 16 nm AMD Artix UltraScale+ FPGA and performs hardware-level reimplementation of the N64 — not software emulation. Multiple outlets note it runs "an enhanced version of the MiSTer N64 core." ModRetro states the FPGA core and firmware are open-source.

**Memory & accuracy.** ModRetro uses four fast PSRAM chips rather than DDR "to get more consistent, low-latency performance." Expansion Pak (8 MB RDRAM equivalent) and Controller Pak are built in. Transfer Pak support is via Chromatic and coming in a firmware update. It is region-free (NTSC & PAL). Recalbox (June 4, 2026) reported "nearly fifty games that may experience bugs of varying severity"; ModRetro's own M64 compatibility database subsequently listed 276 NTSC titles as "no issues" and 16 as "in progress" (per 80.lv, July 2026) — the in-progress set including Donkey Kong 64, Perfect Dark, Rogue Squadron, and Jet Force Gemini. ModRetro pushes wireless firmware updates. Overclocking is supported (standard mode at launch, an "advanced mode" exploiting the PSRAM architecture promised via firmware).

**I/O.** HDMI up to 4K@60 with CRT/scanline filters; a separate CRT AV adapter (composite/component/S-Video/RGB) is a preorder accessory. Rear I/O: one USB-C power port, an HDMI port, a microSD slot (16 GB card included), and **two data-capable USB-C "accessory" ports whose documented purpose is charging M64 Pro controllers** and firmware update. Four front controller ports; compatible with original N64, M64 Pro, Hyperkin Captain+, Retro Fighters, 8BitDo 64, and NSO controllers (via accessory).

**Audio path.** The M64's published spec is "CD-quality uncompressed audio (48 kHz 16-bit PCM)" over HDMI. This is a key detail for DSP work: the console reclocks/reconstructs N64 audio to a fixed 48 kHz HDMI stream. The real N64 AI, by contrast, derives its rate from a clock divider off the video clock (NTSC ~48.68 MHz), so target rates like 22.05 k/32 k/44.1 k are only approximations. Your Faust output rate should be chosen for the N64 AI, not the M64's HDMI rate — the M64 will resample whatever the core produces.

**Flashcart compatibility.** Reviewers confirm the M64 "handled the SummerCart with zero issues" (fast ROM loading, excellent compatibility). Per The Shortcut's M64 review, "by the time the first units ship to customers, an over-the-air firmware update will add EverDrive-64 X5 and X7, and Summercart 64 compatibility"; the X7 was still "getting some of its performance smoothed over by the ModRetro team" at launch. There is **no cartridge-slot USB debug path** on the M64 — the accessory USB ports are not wired to the PI bus — so you cannot use UNFLoader-style USB stdio against the M64 itself.

**Verdict for homebrew dev.** The M64 is a deployment/QA target, not a devkit. Compared to a real NUS-001, the M64 adds convenience (fast boot, 4K, overclock) but removes the analog audio path and abstracts the AI clocking. Compared to the Analogue 3D (also FPGA, $249.99, shipped late 2025 after multiple delays over a two-year period), the M64 is $50 cheaper and its core/firmware are stated to be open-source, which matters if you need to reason about audio timing accuracy. For DSP validation you should still confirm on original hardware, because both FPGA consoles reconstruct rather than reproduce the analog DAC behavior your ear may be tuned to.

### 2. N64 Audio Architecture for DSP

**VR4300 CPU.** NEC VR4300 (CPU-NUS) at 93.75 MHz, MIPS III, 5-stage in-order scalar pipeline, 16 KB I-cache / 8 KB D-cache, 32-bit external system bus, ~125 Dhrystone MIPS. Critically, per the Nintendo 64 technical specifications wiki, "there is no dedicated physical FPU datapath on the VR4300; instead, the integer pipeline is shared for this purpose, meaning that floating-point instructions will stall the pipeline" (Multicycle Instruction Interlock). Sourced instruction latencies (in cycles; latency == throughput because the FP/multiply unit is not pipelined — triple-corroborated from GCC's `mips/4300.md` scheduler model, the SGI/MTI R4300 RISC Processor Spec v2.2, and n64brew, all transcribing the NEC VR4300 User's Manual):

| Op | Single (.S) | Double (.D) |
|---|---|---|
| ADD/SUB | 3 | 3 |
| MUL | 5 | 8 |
| DIV | 29 | 58 |
| SQRT | 29 | 58 |
| int MULT / DMULT | 5 / 8 | — |
| int DIV / DDIV | 37 / 69 | — |
| FP move/abs/neg/cmp | 1 | 1 |

A double-precision divide is **58 cycles ≈ 0.62 µs** — at 44.1 kHz you have only ~2,126 total CPU cycles *per sample* even if you owned the whole CPU, so a single `DIV.D` burns ~2.7% of the entire per-sample budget. `DIV.D` is exactly 2× `DIV.S`, and `MUL.D` (8) is 1.6× `MUL.S` (5). There is also the well-known VR4300 multiply bug (sNaN/0/Inf operands corrupt back-to-back multiplies); GCC's `-mfix4300` inserts NOPs after `mul.s`/`mul.d`/`mult` — keep it enabled. The oft-quoted "93.75 MFLOPS" is a 1-FLOP/clock marketing peak, not a sustained rate.

**RSP (Reality Signal Processor).** A stripped-down MIPS core = Scalar Unit (SU) + a COP2 Vector Unit (VU) with 32× 128-bit registers organized as **8 lanes of 16-bit each** (like SSE2 EPI16). One SU and one VU op can issue per clock if interleaved; RSP runs at 62.5 MHz. Only **4 KB IMEM** (instructions) and **4 KB DMEM** (data), no external bus — a DMA engine moves code/data between IMEM/DMEM and RDRAM, drivable by either CPU or RSP. SGI's RSP Programmer's Guide notes the RSP can do "500,000,000 multiply-accumulate operations per second" at 62.5 MHz with the 8-element vector pipeline. This is the workhorse for any serious on-console DSP, but the 4 KB DMEM working set is the binding constraint: delay lines and tables mostly must live in RDRAM and be DMA'd in/out in blocks.

**AI (Audio Interface).** Very simple: per the n64brew wiki, "it fetches samples via DMA from RDRAM at a specified rate, and then outputs them. It performs absolutely no conversion on the samples: any audio processing functionality (decompression, mixing, etc.) must be performed by either the CPU or the RSP." Rate is set by `AI_DACRATE` (a clock divider off the video clock — NTSC VI clock ≈ 48.68 MHz, so `DACRATE = VI_CLOCK/freq - 1`). "The AI does not have an internal RAM holding samples: the DMA is directly connected to the DAC." Unusually, the AI IRQ fires when a buffer *starts* playing (double-buffer pacing), not when it ends. It handles 16-bit signed interleaved-stereo. libdragon and moria.us both document the standard 2-in-FIFO-plus-1-pending triple-buffer scheme to avoid underruns; the buffer must be cache-flushed before the AI reads it.

**RDRAM & contention.** 4 MB (9-bit bus, 9th bit for AA/Z), 562.5 MB/s peak shared across CPU/RSP/RDP, but **~640 ns access latency** dominates real-world behavior — it is very easy to be latency-bound long before saturating bandwidth. The CPU cannot DMA to RDRAM itself and must go through the RCP. Every RSP audio task competes with RDP command-list generation and graphics DMA for the same bus, so an audio microcode that thrashes DMEM steals frame time from graphics.

**Per-frame budget.** A 60 Hz NTSC frame = 1,562,500 CPU cycles. Traditional N64 audio ran the RSP audio microcode once per frame to synthesize a frame's worth of samples. At 22.05 kHz you produce ~367 samples/frame; at 32 kHz ~533; at 44.1 kHz ~735. libdragon's mixer reference point: a 10-channel XM plays at "< 3% CPU and < 10% RSP," i.e. sample playback + mixing is cheap; *synthesis* is what's expensive.

### 3. Toolchain and SDK Options

**Use libdragon.** Repo: DragonMinded/libdragon; docs at libdragon.dev; N64brew wiki. Key properties: modern GCC 14 + Newlib, full C11, a 64-bit-capable ABI (unlike libultra's 32-bit ABI, so you can use true R4300 64-bit ops), open-source IPL3 for fast boot and compressed code. Audio subsystem: RSP-accelerated mixer up to 32 channels, streaming from ROM; `wav64` (uncompressed = level 0, VADPCM = level 1 default, Opus = level 3); `audioconv64` with `--wav-compress` (VADPCM) and `--wav-resample`; `xm64player` and `ym64player` for tracker music. Core API: `wav64_load()`/`wav64_play()`, `mixer_ch_play()`/`mixer_ch_stop()`. Recent VADPCM added a Huffman layer (+2–5% ratio); VADPCM compressed files default to concurrency factor 4, Opus to 1.

**RSP microcode toolchain.** libdragon provides `rspq` (a command-queue engine dispatching to overlays, auto-loading overlay IMEM as needed — each command's MSB is an overlay ID + command index) and `rsp.h` (`DEFINE_RSP_UCODE`, `rsp_load`, `rsp_run`/`rsp_run_async`/`rsp_wait`, direct `SP_DMEM` access). Microcode is written in RSP assembly (GNU `as` with cop2/lwc2/swc2 macros defined in `ucode.S`) or, far more productively, in **RSPL** (HailToDodongo's high-level GLSL-like transpiler used by Tiny3D) which exposes `dma_in`/`dma_out`/`dma_in_async`, a `state` section that persists across overlay switches, and vector types. RSPL is your realistic route to custom audio microcode.

**Debug/USB.** UNFLoader (buu342) is the cross-cart USB ROM uploader + debug library (usb.c/debug.c for both libultra and libdragon); libdragon's `debugf()` is redirected to the PC console over USB on 64drive/EverDrive/SC64, and UNFLoader now supports **GDB** (qSupported, g/G, m/M, Z0/z0, c, Ctrl+C) for both SDKs across 64Drive HW1/HW2, EverDrive 3.0/X7, and SummerCart64.

**libultra / modern SDK route.** libultra gives you the classic `alSeqPlayer`/`alSynth` audio library and the Nintendo ABI audio microcode. It's the historically authentic path and its sequence-player ABI is well documented (Zelda64 audio format on HackMD; ultra64.ca manuals). But it's a 32-bit ABI, less ergonomic, and its emulator/tooling story is worse for homebrew. **Recommendation: libdragon.**

**Nix packaging.** No first-class nixpkgs derivation exists, but the toolchain is a standard `mips64-elf` GCC/binutils/newlib cross-compiler (the n64-tools/gcc-toolchain-mips64 repo automates exactly this using libdragon's own build script — GCC 12.2/Newlib 4.2/binutils 2.39 in a recent build). `pkgsCross` in nixpkgs already exposes generic embedded cross targets; building a `mips64-elf` cross toolchain + a libdragon derivation that sets the `N64_INST` environment variable to a store path is a straightforward flake for someone who already builds custom NixOS distros. Expect to write the derivation yourself (and Faust is already in nixpkgs).

### 4. Faust → N64 Real-Time (On-Console)

**Compilation path.** Use `faust -lang c` (or `-lang cpp`) to emit a self-contained, library-free `compute()` that works at sample level with constant memory — exactly what you want for bare metal (Faust's generated code "is self-contained and does not depend on any DSP library or runtime system … has a very deterministic behavior and a constant memory size"). Write a minimal libdragon "architecture file" that: allocates non-interleaved float buffers, calls `init(sampleRate)` with your chosen AI rate, and calls `compute(nframes, in, out)` to fill the audio buffer you then hand to libdragon's mixer or a raw AI double-buffer. `FAUSTFLOAT` must be `float` (single). Use `-single`. Use `-os` (one-sample) if you drive it sample-by-sample from a control loop; `-inpl` (in-place, scalar mode only) if input and output buffers alias. Use `-mem` / a custom memory manager to place delay-line and table state deliberately (small tables in D-cache-friendly regions; large ones accessed carefully because of the 640 ns RDRAM latency).

**Killing libm.** Faust's `maths.lib` maps `tanh`, `exp`, `sin`, `pow`, etc. to libm, which is both large and slow on the VR4300. Replace them with table lookups filled at init via `ba.tabulate`/`ba.tabulateNd` (auto-generated LUTs over a bounded domain with linear interpolation), or with `rdtable` populated by an init-time integer counter. For a physical-modeling instrument, pre-tabulate the nonlinear excitation (`tanh` saturation, reed/bow tables) — standard Faust practice that maps perfectly to N64 constraints. Note that Faust already computes `pow` with integers when both arguments are integers.

**Fixed-point status — do not count on it.** Faust has an experimental `-fx` fixed-point option (added ~v2.33) and `fixedpointprecision` variant statements, but GRAME/INSA's own **FAST project final report states the compiler "is still not capable of producing fixed-point code in a generalized way,"** and that fixed-point management "did not progress enough during FAST to result in an operational system that can be generalized to all Faust programs." The academic prototype (Herrou/de Dinechin/Letz/Orlarey/Volkova, arXiv 2403.06527) targets the `ap_fixed` HLS library for FPGAs (Syfala toolchain), not general MIPS integer codegen. **Conclusion:** you cannot today press a button and get correct N64 fixed-point from Faust. The Syfala/faust2fpga path is for Xilinx Zynq boards (Zybo Z7), irrelevant to the N64's fixed MIPS RSP. Fixed-point on N64 means hand-porting (below).

**Numerical consequences of dropping `-double -ftz 2` → single.** The crux for physical modeling:
- **Waveguides / long delay lines:** interpolation coefficients and loop gain are fine in single precision; the risk is slow DC/limit-cycle drift in very-long feedback loops. Single float (24-bit mantissa) is generally adequate for waveguide strings/tubes at audio rates — the classic Smith/CCRMA implementations run in single precision.
- **High-Q resonators / biquads:** the danger zone. Near-unity-pole biquads in Direct Form I/II lose coefficient resolution in single precision and *ruinously* in naive 16-bit fixed point. Mitigations: transposed Direct Form II, or state-variable / normalized-ladder / coupled-form structures robust to coefficient quantization; keep resonator state in higher precision than the I/O (32-bit accumulation on the RSP VU accumulator).
- **Allpass / Thiran dispersion filters:** coefficient sensitivity rises with order and Q; keep these single-precision float on the CPU rather than 16-bit RSP fixed point, or split into cascaded first-order sections.
- **Feedback loops generally:** `-ftz` matters because denormals on the VR4300 are handled via exception, which is expensive and precisely why libultra's context switch explicitly saves FPU state (the n64.readthedocs.io note about distorted audio from unsaved COP1 registers is this hazard). Set FCR31 flush-to-zero/round mode explicitly, and design loops to avoid denormal decay tails (inject tiny DC or a leakage term — the practical equivalent of your `-ftz 2`).

**What's realistic in real time at 93.75 MHz (CPU, single precision).** Budget math: one 44.1 kHz sample = ~2,126 CPU cycles *if you owned the whole CPU*, but a game needs most of it. Assume ~15–25% of CPU for audio → ~320–530 cycles/sample. A single-precision biquad ≈ 5 MUL + 4 ADD + loads ≈ 40–60 cycles → **~6–10 biquads/sample**. A single waveguide voice (two interpolated delay reads + loss filter + fractional-delay allpass) ≈ a few hundred cycles → **1–3 simultaneous waveguide voices** is realistic on the CPU alone; a full 8+-voice polyphonic PM instrument is not, unless offloaded to the RSP. Anything with per-sample `DIV.S` (29 cycles) or `exp`/`tanh` via libm must be tabulated. **Static polyphony** (fixed `-nvoices`, no dynamic allocation) is mandatory for deterministic budgeting.

**Hand-porting inner loops to RSP microcode.** The RSP's 8×16-bit VU can compute 8 biquads or 8 delay taps in parallel, and VADPCM already proves 16-bit SIMD audio works well there (the "V" in VADPCM reflects vectorized decode on the 8-lane SIMD). Strategy: (1) keep Faust as design/reference (compile `-double` on PC for golden output); (2) identify the hot inner loop (biquad bank, comb/allpass bank, waveguide junction); (3) reimplement in RSPL as a fixed-point (Q1.15 or Q1.31 split-word) 8-lane kernel; (4) validate against the Faust double output. The RSP excels at **parallel, low-feedback** structures (FIR, parallel biquad banks, additive/wavetable, reverb combs) and is poor for **tight serial feedback with high Q** (keep those on the CPU in single float, or use careful 32-bit VU-accumulator math).

### 5. Faust → N64 Offline / Sample-Baked

Where you get the most sonic bang. Render your Faust PM instruments offline (on your NixOS box at `-double -ftz 2`, full quality) to WAV, then:
- **VADPCM encode** via `audioconv64 --wav-compress` → `.wav64` (level 1). VADPCM is a 4-bit ADPCM variant decoded on the RSP's 8-lane SIMD — cheap at runtime and RAM-resident (the AI DMA can only read RAM, not ROM, so samples must be decompressed into RAM).
- **Opus streaming** (`wav64` level 3) for long musical cues from ROM/SD at realtime playback rate with very high compression.
- **Multisampling / loop points / round-robin:** design instruments as sample sets keyed by pitch/velocity with sustain loop points and round-robin variants (avoid machine-gunning), mapped to mixer channels with per-channel pitch via resampling.
- **Sequencing:** libdragon's **XM64** (FastTracker/MilkyTracker/OpenMPT; "10-channel XM at <3% CPU / <10% RSP") is the pragmatic music engine; YM64 (Arkos Tracker 2) for chiptune. For adaptive/interactive music, write a small custom sequencer that triggers wav64 one-shots and controls the few live Faust voices. libultra's `alSeqPlayer` (MIDI-like sequence + soundbank) is the authentic alternative on the SDK route.
- **ROM/RAM budgets:** original carts were 4–64 MB; per the SummerCart64 README it has "64 MiB SDRAM memory for game and save data … 16 MiB FLASH memory for bootloader and extended game data (with extended memory flashcart supports game ROMs up to 78 MiB)," plus microSD streaming — so you are not cart-size-limited in development. Budget **RAM** (4 MB, or 8 MB with the M64's built-in Expansion Pak), not ROM, as your true constraint: per N64 Squid a 10-second stereo clip at standard rate is "almost 2 megabytes — that's half of the N64's RAM," so VADPCM/streaming is essential.

**Hybrid recommendation:** bake ~80–90% of the instrument (bodies, sustains, complex PM timbres) to VADPCM multisamples + XM64 sequencing; reserve live single-precision Faust for the ~10–20% that must be parametric/interactive (real-time excitation, continuous pitch bends on 1–3 waveguide voices, per-note morphing). This mirrors how the N64's best-sounding games worked.

### 6. Networking for the SSHitunneller! N64 Port

**Native N64 networking is a dead end.** Historical options: the Morita Shogi 64 built-in RJ-11 modem; the 64DD RandNet modem (28.8 kbps dial-up, only ~15,000 subscribers ever, JP-only, defunct since 2001); and the SharkWire. All rare, slow, and offline. The M64 has WiFi/Bluetooth but only for firmware/controllers — it exposes **no** game-accessible network API to the cartridge.

**The real path: flashcart USB + host-PC proxy.** buu342's **N64-NetLib** (released Dec 10, 2024) is your template. It leverages the flashcart USB port for internet connectivity: an N64 C library (libultra *and* libdragon), a C++/wxWidgets client app acting as "server browser and USB tether," Java master + game servers. Per the NetLib page, "Everything is designed to work using UDP, and implements a reliability system not too different from Valve's GameNetworkingSockets" — with prediction, reconciliation, and interpolation demonstrated in the realtime example. It builds on his UNFLoader USB library; SummerCart64, 64drive, and EverDrive X7 all expose USB.

**Architecture for SSHitunneller!:**
```
[Rust SSH server] ──SSH / DCF-Audio codec_id 2──▶ [Host-PC proxy]
                                                     │  (terminates SSH,
                                                     │   speaks simple binary
                                                     │   protocol over USB)
                                                     ▼
                                          [flashcart USB, ~23.8 MiB/s peak]
                                                     ▼
                                          [N64 client: decode control data,
                                           drive live Faust-PM synthesis]
```
The proxy terminates SSH (the N64 cannot do crypto at useful rates), unpacks your DCF-Audio codec_id 2 control stream, and forwards **control data only** — note/gate/pitch/parameter frames — to the cart over USB. The N64 runs the same Faust-PM voice model client-side and synthesizes locally, exactly as your DCF-Audio design intends. This is ideal for N64: you send bytes-per-frame of control, not audio.

**Throughput/latency.** Per the SummerCart64 README: "8 kiB on-chip buffer for general use · ~23.8 MiB/s peak transfer rate USB interface for data upload/download and debug functionality." SC64 also added cart interrupts (button / command-finish / USB-data-waiting) and an **AUX register + `AUX_WRITE` USB command as "a simple message link between PC and N64"** — purpose-built for your control tunnel. Realistic sustained small-packet round-trip is low-single-digit milliseconds for the USB hop, dwarfed by internet RTT to the Rust server. Control-rate data (60–240 Hz parameter frames × tens of bytes) is trivially within budget. EverDrive X7's USB is much slower — the SC64 author calls it "a disappointment for homebrew development (slow USB upload)." **Use SummerCart64.** On the M64 specifically, with no cart USB, an M64 unit cannot participate in a live session — networking requires original/clone hardware with a SummerCart64. Client-side Faust synthesis driven by streamed control data is feasible; the limiting factor is synthesis CPU budget (Section 4), not the link.

### 7. Development Workflow

**Flashcart:** **SummerCart64** is the clear winner — open-source (GPLv3), ~23.8 MiB/s USB and microSD, 8 KiB buffer, native libdragon/libcart/UNFLoader support, GDB, IS-Viewer64 emulation, well-documented command protocol, cart interrupts, and the AUX PC↔N64 message channel. 64drive is excellent but out of production/restock. EverDrive X7 works but has slow USB. All three load libdragon ROMs; SC64 is confirmed working on the M64.

**Emulators:** **Ares** is the reference — libdragon states it is "the only emulator that accurately emulates the hardware" for homebrew, with a "Homebrew mode" toggle enabling developer checks; "you can develop 99% of your game using libdragon and the Ares emulator, and be confident that the game will correctly run on hardware." CEN64 is cycle-accurate but too slow for comfortable iteration (audio choppy, frames dropped even multithreaded). gopher64 and Simple64 exist but trust Ares for RCP/RSP behavior. **However:** for *DSP* work specifically, do not fully trust any emulator's audio — the AI's clock-divider rate approximation, RDRAM latency contention, and denormal/FPU-flush behavior are exactly what emulators get subtly wrong. Iterate in Ares, but **cycle-count and A/B listen on real hardware** (a real NUS-001 for analog truth, then the M64 for FPGA-path validation).

**Profiling:** use the VR4300 hardware count register / libdragon `TICKS`, `rspq` profiling, and `debugf()` over USB to log per-frame synthesis cycle counts. Budget against 1,562,500 cycles/frame (NTSC 60 Hz) and the per-sample figures in Section 2.

**Examples worth studying:** libdragon's `mixer`/audio examples and `ucodetest`; **Tiny3D** and its RSPL microcode (HailToDodongo) as the model for writing your own audio ucode; **Pyrite64** (libdragon+tiny3d engine/editor); N64-NetLib's realtime example for the networking model; the Zelda64 audio format writeup (HackMD) and the meauxdal N64-AI-Test-ROM for AI/DAC behavior characterization; the moria.us "Basic Audio" series for raw AI double-buffering; the `command-tab/awesome-n64-development` and n64.dev curated lists.

## Recommendations

**Stage 0 — Toolchain (week 1).** Build a `mips64-elf` GCC/newlib cross-toolchain and a libdragon derivation as a Nix flake pinning `N64_INST` to a store path; add Faust (nixpkgs) and audioconv64. Acquire a SummerCart64 and a real N64 (NUS-001); keep the M64 as a QA box. Set up Ares in Homebrew mode + UNFLoader/GDB over SC64 USB.

**Stage 1 — Baked audio spine (weeks 2–4).** Render existing Faust PM instruments offline at `-double -ftz 2`, VADPCM-encode via `audioconv64`, and get an XM64-sequenced music bed + wav64 multisample instrument playing through libdragon's mixer. De-risks the whole audio path and yields shippable sound immediately.

**Stage 2 — Live single-precision Faust voices (weeks 4–8).** Port 1–3 waveguide/PM voices via `faust -lang c -single -os`, with all `tanh`/`exp`/`sin` replaced by `ba.tabulate` LUTs and a libdragon architecture file. Profile cycles on hardware. **Threshold: if one voice exceeds ~500 cycles/sample at 32 kHz, drop the output rate to 22.05 kHz, reduce voice count, or move the inner loop to the RSP.**

**Stage 3 — RSP microcode offload (optional, weeks 8+).** Only if Stage 2 is CPU-bound: reimplement the parallel biquad/comb bank in RSPL as a Q1.15 8-lane kernel, validated against the Faust double reference. Keep high-Q feedback loops on the CPU in single float.

**Stage 4 — Networking (parallel track).** Fork N64-NetLib. Write the host-PC proxy that terminates SSH from your Rust server and forwards DCF-Audio codec_id 2 control frames over SC64 USB (use the AUX register channel). Drive the Stage-2 live voices from the streamed control data. Target ≤5 ms USB-hop latency; if control-frame jitter causes artifacts, add a 1–2 frame client-side interpolation buffer (the NetLib realtime example already demonstrates this).

**Decision thresholds that change the plan:**
- If ModRetro ships a documented cartridge-side debug/USB interface in firmware → reconsider the M64 as a primary dev target.
- If Faust's fixed-point backend reaches general MIPS-integer maturity → revisit automated RSP codegen instead of hand-porting.
- If live-synthesis CPU budget forces <1 voice → go fully sample-baked and use live Faust only for real-time *effects* (filter sweeps, a single continuous drone) rather than polyphony.

## Caveats
- **M64 internals are partly unverified.** ModRetro states the core/firmware are open-source and audio is 48 kHz/16-bit PCM, but detailed audio-timing accuracy vs. NUS-001 (AI clock reconstruction, jitter) is not independently benchmarked in the sources found; treat 48 kHz as the HDMI output rate, not the internal N64 AI behavior. Compatibility caveats (276 "no issues" / 16 "in progress" NTSC titles per ModRetro's July 2026 database) are per ModRetro's own list and are being patched OTA.
- **FPU cycle counts** are triple-corroborated (GCC `4300.md`, SGI/MTI R4300 Spec v2.2, n64brew), all transcribing the NEC VR4300 User's Manual; "93.75 MFLOPS" is a nominal 1-FLOP/clock peak, not sustained.
- **Faust fixed-point** is explicitly described by GRAME's own FAST project as not yet generalizable; any claim that Faust can auto-target N64 fixed point would be wrong today.
- **USB throughput** (~23.8 MiB/s SC64 peak) is a peak bulk-transfer figure; small-packet control-tunnel latency was not directly measured in sources and is inferred to be low-single-digit ms — validate empirically.
- **The M64 cannot be a live networked client** given no cart USB; SSHitunneller! N64 play requires original/clone hardware + SummerCart64.
- Prices, availability, and firmware features are as of the July 28, 2026 launch window and ModRetro's ongoing OTA updates; verify current firmware capabilities before committing to any M64-specific behavior.
