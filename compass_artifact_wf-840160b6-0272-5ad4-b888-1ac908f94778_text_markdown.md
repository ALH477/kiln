# Is a WebAssembly Port of `ALH477/kiln` Feasible? A Technical Assessment

## TL;DR
- **Yes, a browser/WebAssembly port of kiln's *game logic* is realistic and is the single most promising path — but only if kiln's engine layer is refactored to render/audio/input through a swappable "host" backend, because today the engine sits directly on N64-only hardware libraries (libdragon's rdpq/RDP, Tiny3D RSP microcode, the RSP audio mixer) that have no browser equivalent.** kiln is written in C, so Emscripten can compile the portable parts; the hard work is re-implementing the rendering and audio backends against WebGL2 and Web Audio.
- **The most practical route is a source-level Emscripten port with a new WebGL2/Web Audio "host" backend (mirroring exactly what Dominic Szablewski did for the libdragon/Tiny3D game *Xibalba 64*, whose engine already builds to WASM via SDL2/Sokol backends).** Running the compiled `.z64` inside a WASM N64 emulator (n64wasm/ParaLLEl) is a lower-effort but lower-quality fallback; static recompilation (N64Recomp) to WASM is technically conceivable but currently impractical for this engine.
- **Kiln itself is a very early-stage, single-author project (5 commits, 1 star, no host/desktop/WASM target mentioned anywhere in its docs), and it already exposes a clean high-level engine API (`kiln_frame_begin`, `kiln_scene_begin`, `kiln_gui_panel`).** That API surface is the natural "seam" to port behind — meaning the effort is significant but bounded, not impossible.

## Key Findings

**What kiln actually is.** Despite being described casually as "an N64 game engine," kiln's own README calls it "*a Nix build system for Nintendo 64 / Analogue 3D / ModRetro M64 software, with a Faust DSP bridge that enforces the console's numeric limits at build time.*" It bundles: a `mips64-elf` GCC 14.4.0 cross-toolchain, the **libdragon** SDK (preview branch), **Tiny3D** (an RSP-accelerated 3D microcode library), the **Faust** DSP compiler, and the **Ares** emulator — all pinned hermetically via a Nix flake. The engine component (`libkiln`) is described as "*3D on Tiny3D, 2D GUI on rdpq, actors/rooms/camera/skeletal-animation runtime, audio on the RSP mixer.*" It is written in **C** (GitHub topics list `c`, `faust`, `n64`, `nix`, `blender`).

**Maturity.** The repository has only **5 commits**, **1 star**, **0 forks**, **0 watchers**, and no tagged releases. It is a single-author (ALH477 / DeMoD LLC) early-stage project. Development explicitly targets **real N64 hardware (NUS-001) with a SummerCart64**; the ModRetro M64 is a "deployment and FPGA-validation target only." There is **no mention of WebAssembly, Emscripten, a PC/desktop build, or cross-platform support anywhere in the README.** The "feasibility report" the README repeatedly references is about *N64 hardware numeric constraints* (VR4300 cycle budgets, no-FPU transcendental bans, VADPCM audio), not about portability.

**The one encouraging structural signal.** The repository contains a top-level `plat/host` directory path. This suggests the author has at least begun carving out a platform-abstraction namespace whose first member is a non-N64 "host" target. However, GitHub flags this path with "This path skips through empty directories," and there is no corroborating evidence (in the README or elsewhere) that it contains a working desktop window/render/input/audio implementation. It appears to be scaffolding rather than a functional backend.

**The engine already has a clean API seam.** Game code calls high-level engine functions, not raw hardware:
```
kiln_frame_begin();            // attach framebuffer + Z-buffer
  kiln_scene_begin(&scene);    // 3D: Tiny3D, perspective, lit, depth-tested
  ... geometry ...
  kiln_gui_begin();            // depth OFF, screen space
  kiln_gui_panel(...); kiln_gui_text(...); kiln_gui_bar(...);
  kiln_gui_end();
kiln_frame_end();              // present
```
This matters enormously for portability: game logic is insulated from the RDP/RSP. The *implementation* of these `kiln_*` calls, however, is N64-native (Tiny3D microcode, rdpq, libdragon's built-in font, RSP mixer).

**Decisive prior art.** The closest possible analog was published on **August 4, 2026**: Dominic Szablewski's **Xibalba 64**, a commercial libdragon + Tiny3D N64 game published physically for the ModRetro M64 — the exact same hardware kiln targets. (Szablewski notes it is "only the second physical release of any *new* N64 game since the end of the console's original commercial life... No other new games have been published for the N64 since Tony Hawk's Pro Skater 3 in 2002.") Its engine, `high_impact` (a C rewrite of his Impact engine), was "designed from the start to support multiple platform backends. I had SDL2 and Sokol working, which meant Windows, macOS, Linux, and even WASM. Adding N64 support was just another backend." He is explicit about the modularity: "Out of the box, high_impact comes with two platform backends (SDL2 and Sokol)... The rendering backend in high_impact is also modular. You can compile your game with a software renderer, OpenGL or Metal (for iOS/macOS)." He confirms: "It took me only a few evenings to build a new platform backend for high_impact on top of libdragon." Throughout development he "retained the ability to build the game with the SDL2 or Sokol backends... great for playtesting game logic." His level compiler even "writes those values in big-endian format for the N64 and little-endian format for x86 (SDL2, Sokol, WASM), so we can easily read everything on all platforms without byte swapping." **This is a working, shipped proof that a libdragon/Tiny3D-architected N64 game can also target WASM — via a portable engine core with swappable backends, not by porting libdragon itself.**

## Details

### Step 1 — Engine technical profile

- **Language:** C (C11 via GCC 14). This is the single most favorable fact for a WASM port: Emscripten's core competency is compiling C/C++ to WASM, and it "provides Web support for popular portable APIs such as OpenGL and SDL2."
- **Toolchain/SDK dependency:** libdragon (preview branch) is the foundational SDK, plus Tiny3D for 3D. libdragon is an open-source N64 SDK (Unlicense); it explicitly "targets real N64 hardware and uses many advanced corners of the hardware not used by old commercial games." kiln pulls libdragon and SummerCart64 only as Nix flake inputs; they are "never vendored... never linked into anything here" except through the normal libdragon `make` build.
- **Rendering:** Hardware-based. 3D goes through Tiny3D, which "comes with both RSP microcode and an easy to use C-API around it" and is "the equivalent of always running in GL_RDPQ_MATERIAL_N64 mode." 2D/GUI goes through libdragon's **rdpq**, which drives the **RDP** (the N64's rasterizer GPU) via the **RSP**. There is no software rasterizer in the engine's main path — it depends on real RCP (Reality Coprocessor) hardware.
- **Audio:** libdragon's **RSP mixer**, with a Faust DSP bridge that either compiles Faust `.dsp` voices to VR4300 (CPU) objects or bakes them offline to **VADPCM** (`.wav64`). The README warns "do not trust any emulator for audio work — the AI's clock-divider rate, RDRAM contention, and denormal handling are exactly what emulators get subtly wrong," underscoring how hardware-coupled the audio path is.
- **Low-level hardware assumptions:** The build system's "gates" reveal deep hardware coupling: it fails the build if double-precision instructions reach the ROM ("DIV.D is 58 cycles against a ~2126-cycle per-sample budget at 44.1 kHz"), if the toolchain stops "producing big-endian R4000-family code," or if a `.z64` "comes out byte-swapped." The cycle-budget estimator is "instruction counts weighted by the VR4300 latency table." The target is a 93 MHz big-endian MIPS VR4300 CPU paired with the RDP and programmable RSP coprocessors. These are ROM-side constraints (they concern what runs *on* the N64), and they would not apply to a WASM/host build — but they confirm the codebase currently assumes a big-endian MIPS target.

### Step 2 — WASM porting approaches

**(a) Source-level Emscripten port with a WebGL2/Web Audio host backend — RECOMMENDED.**
This is the approach validated by Xibalba 64/high_impact. The plan: compile kiln's portable game-logic and engine-runtime C code (actors, rooms, camera, skeletal animation, scene graph, immediate-mode GUI logic) with Emscripten, and replace the N64 backend of the `kiln_*` API with a new backend that renders via **WebGL2**, plays audio via the **Web Audio API**, and reads input via the **Gamepad API**. Emscripten "converts OpenGL into WebGL" and ships an SDL2 port (`--use-port=sdl2`), so a host backend can be built on SDL2+OpenGL ES/WebGL2 or on Sokol (`sokol_gfx.h` "unifies OpenGL 3.3, WebGL 2, Direct3D 11, and Metal") exactly as high_impact does.

*Does libdragon itself have an Emscripten backend?* No. libdragon is a bare-metal N64 SDK with no PC/host or browser target; the community approach (per Xibalba 64) is **not** to port libdragon to the browser, but to abstract the *engine* above libdragon and write a parallel desktop/WASM backend. Kiln's existing `plat/host` directory suggests its author may already intend this pattern, but no working host backend is evidenced yet.

*Effort:* Moderate-to-significant. The engine's rendering and audio are described as sitting directly on Tiny3D/rdpq/RSP-mixer. Every `kiln_scene_begin`/`kiln_gui_*` call, and the Tiny3D model/skeletal-animation and VADPCM/Faust audio paths, would need host-side reimplementation. If the code is cleanly factored behind the `kiln_*` API (and `plat/host` becomes a real backend), this is "a few evenings to a few weeks" per the Xibalba 64 precedent for the plumbing, plus real work to match the N64 look (texture formats, 5/5/5/1 color, 4KB TMEM-driven asset layout). If it is not cleanly factored, it is a larger refactor.

**(b) Full-system N64 emulation compiled to WASM — LOWEST EFFORT, LOWEST QUALITY.**
Build the ROM normally, then run the `.z64` inside a browser N64 emulator. Working precedents exist: **n64wasm** (nbarkhina, ~646 stars / ~151 forks) is "a port of the excellent RetroArch ParaLLEl Core to WebAssembly," built with Emscripten, with "a good portion of the 3D games playable and at full speed on a mid-range computer," Gamepad support, and save states, and it "Also works on the iPhone 13 and Xbox Series X Browser." There is also an older **mupen64plus via Emscripten** (asm.js) port. **Critical caveat:** libdragon/Tiny3D ROMs need a *cycle-accurate, full-hardware* emulator (Ares/cen64/gopher64), not the HLE emulators that most browser cores are based on. ParaLLEl (the basis of n64wasm) is LLE-capable for RSP/RDP, so it is the most plausible candidate, but there is no evidence anyone has run a libdragon+Tiny3D homebrew ROM in a browser emulator, and RSP-microcode-heavy, RSP-audio-mixer homebrew is exactly the class of software HLE cores handle worst. This path gives you the authentic N64 rendering/audio "for free" but pays a heavy full-emulation performance tax (emulating the VR4300 + RSP microcode interpreter + RDP in the browser) and inherits any accuracy gaps of the ported core — including the audio inaccuracies the README explicitly warns about.

**(c) Static recompilation to WASM — CONCEPTUALLY POSSIBLE, IMPRACTICAL TODAY.**
**N64Recomp** (the tool behind Zelda 64: Recompiled, by Wiseguy) "statically recompile[s] N64 binaries into C code that can be compiled for any platform." Since it emits C, that C could in principle be compiled to WASM by Emscripten — and there is adjacent proof that recompiled/decompiled N64 C runs in a browser: the **GoldenEye 007 "PC Port"** (75% decomp / 25% recomp) was "compiled to WASM via Emscripten" and runs in-browser (author's note: "Most of this was vibecoded... it's probably why the game currently runs slow"). However, N64Recomp requires per-title metadata (an ELF with symbols, typically from a decompilation/disassembly), pairs with the native **RT64** renderer (D3D12/Vulkan/Metal — not WebGL) and the **N64ModernRuntime**, and its **RSP microcode support is limited** — its README states verbatim: "RSP microcode can also be recompiled with this tool. Currently there is no support for recompiling RSP overlays, but it may be added in the future if desired." For a bespoke, actively-changing homebrew engine like kiln — where you *have the C source already* — static recompilation of your own ROM would be a bizarre and far more painful path than simply compiling the source. It is the right tool for closed-source retail ROMs, not for an open-source engine you control.

### Step 3 — Concrete blockers specific to kiln

1. **RSP microcode dependency (largest blocker).** Tiny3D's transform/lighting/clipping and libdragon's audio mixer run as RSP microcode. In a source-level host port this code is simply *not used* — you replace it with WebGL2 vertex processing and Web Audio mixing — but that means the host backend must *reproduce Tiny3D's behavior*, not reuse it. In an emulation port, the browser emulator must interpret this microcode accurately (the ParaLLEl/LLE requirement).
2. **N64-specific graphics semantics.** 4KB TMEM, max 64×64 textures, palettized/4-bit indexed formats, the RDP color-combiner/blender model, and 5/5/5/1 framebuffer color. A WebGL2 backend must convert textures and approximate the combiner via shaders to preserve the intended look; this is craft work, not a blocker per se.
3. **Big-endian vs. little-endian.** kiln currently assumes a big-endian MIPS VR4300 (a build gate enforces it; Szablewski likewise flags the N64's "93 MHz MIPS CPU (big-endian!)"). Any binary asset containers (e.g., its `.streamdb`, `.t3dm` models, VADPCM `.wav64`) baked big-endian for the N64 must be re-baked or byte-swapped for a little-endian WASM host — precisely the dual-endian asset-compiler approach Xibalba 64 used ("big-endian format for the N64 and little-endian format for... WASM").
4. **Audio pipeline.** The Faust DSP bridge is actually a *portability asset*: Faust has first-class WebAssembly/Web Audio backends. Per Letz, Orlarey & Fober ("Compiling Faust audio DSP code to WebAssembly," Web Audio Conference, London, Aug 2017; and the ACM Web Conference 2018 Companion paper, DOI 10.1145/3184558.3185970), the libfaust compiler was "compiled for the Web, thus allowing to have an efficient compilation chain from Faust DSP sources and libraries to audio nodes directly available in the browser." So Faust voices could be recompiled to run in the browser natively. The VADPCM baked instruments and the RSP mixer, however, would need a host-side decoder/mixer (straightforward in C/Web Audio).
5. **Third-party native deps.** libdragon, Tiny3D, and SummerCart64 tooling have **no WASM target** and would be excluded from a host build (they are N64/host-tool only). `streamdb-embedded` (LGPL-2.1) is a plain C library and should compile to WASM cleanly.
6. **Timing/`debugf`/USB/flashcart code** is hardware-only and would be stubbed on the host — trivial.

### Step 4 — Feasibility verdict

**A WebAssembly port of kiln is feasible, and the source-level Emscripten port with a new WebGL2/Web Audio "host" backend is the clearly correct approach.** The determining factors are all favorable in principle: kiln is C; it exposes a clean high-level engine API (`kiln_*`); it already has a `plat/host` namespace suggesting intent; its Faust audio layer has native WASM support; and there is a shipped, real-world precedent (Xibalba 64 / high_impact) proving a libdragon+Tiny3D N64 game can build to WASM through a portable core with swappable backends.

The honest caveat is that kiln, unlike high_impact, was **not** designed backend-first — it was designed N64-hardware-first (its whole reason for existing is enforcing N64 numeric constraints), it is only 5 commits old, and its `plat/host` directory appears to be empty scaffolding. So the effort is real: someone must build the host backend that reimplements Tiny3D-equivalent rendering and RSP-mixer-equivalent audio behind the `kiln_*` API. That is weeks-to-a-few-months of focused work for someone fluent in both the engine internals and WebGL2 — not the "few evenings" it took high_impact (which was already multi-backend).

Ranking of paths by practicality for *this* engine:
1. **Source-level Emscripten + WebGL2/Web Audio host backend** — best quality, best performance, most work up front, aligns with the `plat/host` design hint and industry precedent.
2. **ROM inside a WASM N64 emulator (ParaLLEl-based n64wasm)** — least engineering, but heavy runtime cost, uncertain compatibility with Tiny3D/RSP-audio homebrew, and inherits emulator audio inaccuracies.
3. **Static recompilation to WASM (N64Recomp → Emscripten)** — technically possible, demonstrated for retail games (GoldenEye WASM), but pointless when you own the source and blocked by RSP-microcode/overlay limits.

## Recommendations

**Stage 0 — Confirm the abstraction (1–2 days).** Directly inspect `plat/host/`, the `engine/` headers, and `CLAUDE.md` in the repo to determine whether a platform-interface header (vtable/function-pointer struct) already exists and whether the `kiln_*` implementation routes rendering/audio/input through it. *This single fact sets the entire effort estimate.* Benchmark that changes the plan: if a real platform interface exists, proceed to Stage 1 immediately; if the engine calls Tiny3D/rdpq directly from many call sites, insert a platform seam first.

**Stage 1 — Prove game logic compiles to WASM (days).** Compile the non-rendering, non-audio engine code (actors, rooms, camera, skeletal-animation math, GUI layout logic, `streamdb-embedded`) with Emscripten, stubbing the backend. Confirm big-endian assumptions are isolated to asset loaders. Benchmark: a headless WASM build that ticks the simulation without drawing.

**Stage 2 — Build a desktop host backend first, not the browser one (1–3 weeks).** Follow the Xibalba 64 playbook: implement a native SDL2 (or Sokol) + OpenGL/desktop backend for the `kiln_*` API. This is far easier to debug than WASM ("Debugging in WebAssembly is practically non-existent other than logging print statements"). Add a dual-endian asset compiler (big-endian for `.z64`, little-endian for host/WASM). Benchmark: `engine-demo` (the lit spinning cube + HUD, which the README claims runs at 59.8 fps on hardware) runs on desktop through the host backend.

**Stage 3 — Retarget the host backend to WASM (days-to-weeks).** Recompile the SDL2/Sokol backend with Emscripten (`-sUSE_WEBGL2`, `--use-port=sdl2` or Sokol's WebGL2 path), wire input to the Gamepad API, and route Faust voices through Faust's WebAssembly/Web Audio backend while decoding VADPCM in a Web Audio worklet. Benchmark: `engine-demo` runs at interactive framerate in Chrome/Firefox.

**Stage 4 (optional, parallel) — Ship a stopgap emulator build.** In parallel, drop a compiled `.z64` into a ParaLLEl-based n64wasm build to give users *something* in-browser immediately, while noting it is emulation with likely audio/accuracy caveats. Abandon this once Stage 3 lands.

**Do not** pursue static recompilation for this engine; it is the wrong tool when you control the C source.

## Caveats
- **Repo-internals uncertainty.** GitHub's file-viewer subpaths for this obscure 1-star repo could not be retrieved during research; findings about `plat/host` contents, the `engine/` headers, and `CLAUDE.md` are inferred from the verified README plus GitHub's rendered directory listing, not from reading those files directly. Stage 0 above exists precisely to close this gap. The core language (C), SDK (libdragon+Tiny3D), rendering (rdpq/RDP + Tiny3D RSP), and audio (RSP mixer + Faust/VADPCM) facts are all directly confirmed from the README.
- **Prior-art dates.** The Xibalba 64 "How to Make a Nintendo 64 Game in 2026" article is dated August 4, 2026, and describes a shipped commercial product; it is the strongest available precedent but is one developer's account. The GoldenEye WASM port is explicitly experimental ("very ugly and full of hacks... fragile and might crash").
- **Performance is unproven for kiln specifically.** No one has (per available evidence) built a WASM version of kiln or any libdragon+Tiny3D engine's browser backend beyond high_impact's general multi-backend claim. Framerate/visual-fidelity parity with the N64 target is an engineering goal, not a guaranteed outcome.
- **"Feasibility report" ambiguity.** kiln's README references a "feasibility report," but that document concerns N64 hardware numeric/DSP constraints, not a PC/WASM port — do not conflate the two.
- **Look-and-feel fidelity.** A WebGL2 host backend will not automatically reproduce N64-specific artifacts (dithering, 5/5/5/1 color banding, TMEM-driven texture seams). Matching the intended aesthetic is discretionary craft work.
